# CLAUDE.md — Kulova Shopify App

## Context
Solo founder project: **Kulova**, AI customer-service chat widget for the Shopify App Store.
English-first product. Flat pricing: Free (~100 conversations/mo), Pro $29/mo, Company $149/mo.
Differentiator: flat pricing, no per-resolution fees (documented pain point of Tidio/Gorgias).
Exit goal 1–3 years. Owner is anonymous, self-serve/inbound only, minimal budget.

## Working rules (IMPORTANT)
- User communicates in Finnish. Keep replies short — long messages go unread.
- ALWAYS double-check before destructive changes. Take a git checkpoint commit before risky edits.
- NEVER touch kulova.com production (repos `kulovav1`, `kulova_backend` main) without explicit user confirmation — live customers use it. Backend changes must stay backward-compatible: legacy clients send `businessId`, Shopify path sends `shopDomain`.
- Never commit secrets. `.env` is gitignored. KULOVA_INTERNAL_KEY value is stored in Vercel (sensitive) and user's password manager only.
- Ask before: production deploys, schema changes, deleting anything.

## Architecture
- **This repo (`~/kulova-app`)**: Shopify embedded app. React Router template + Prisma session storage + theme app extension at `extensions/kulova-widget` (block `kulova_chat.liquid`, uid in `shopify.extension.toml`).
- **Backend (`~/kulova-backend`)** → https://kulova-backend.vercel.app — Vercel auto-deploys from `main`. Endpoints: `/api/chat`, `/api/botinfo` (both accept `shopDomain` OR legacy `businessId`), `/api/shopify-sync` (internal; requires header `x-kulova-key` = env `KULOVA_INTERNAL_KEY`; creates/returns `businesses` row for a shop).
- **Supabase** project `eacfiiscsdqdcoduyzkk`: tables `businesses` (has `shopify_domain` text + unique partial index, `support_email` text, `owner_email` nullable), `conversations`, `messages`, `login_codes`. **RLS hardening in progress — see "Security incident" section below, do not assume old scope-audit RLS notes are still current.**
- **Widget** (`extensions/kulova-widget/assets/kulova-widget.js`) calls backend `/api/chat` with `{message, sessionId, shopDomain}`. Reads shop from `data-shop="{{ shop.permanent_domain }}"`.
- **Vercel project for this app**: `mramalones-projects/kulova-app` → https://kulova-app.vercel.app
- **GitHub**: `kulova-app` → `github.com/Kalluska/kulova-shopify-app` (private, `main` + `kulova-shopify-setup` pushed). `kulova-backend` → `github.com/Kalluska/kulova_backend`. `kulova-landing` (the kulova.com marketing site + dashboard, `~/kulova-landing`) → `github.com/Kalluska/kulovav1`.
- `shopify.app.toml`: application_url + redirect_urls → kulova-app.vercel.app; `scopes = ""` (see below — v1 needs zero access scopes); GDPR webhook subscriptions added; routes exist: `webhooks.customers.data_request.tsx`, `webhooks.customers.redact.tsx`, `webhooks.shop.redact.tsx` — all three fully implemented (see below), not stubs.

Killing the process leaves the store stuck in this state, pointed at a now-dead tunnel, until `dev clean` explicitly restores the active (production) version. ## Security incident: leaked Supabase anon key + RLS hardening (in progress)

**What happened:** a full technical audit (kulova-app + kulova-backend, pre-App-Store-submit) found the Supabase anon key hardcoded in plaintext in `kulova-landing/dashboard.html` (public static page on kulova.com). Combined with `"allow all"` RLS policies on `businesses`/`conversations`/`messages` (RLS enabled but fully permissive) and `login_codes` having RLS off entirely, **anyone who viewed page source could read/modify any customer's business data and private chat conversations directly against Supabase's REST API**, bypassing the backend entirely. Confirmed active/exploitable (not theoretical) by finding the exact hardcoded key and the exact table/column reads/writes it performed.

**Vaihe 1 (done, same day):** disabled the leaked legacy anon/service_role JWT-based API keys in Supabase (Project Settings → API Keys → Legacy → "Disable JWT-based API keys"), then fully revoked the underlying legacy JWT signing secret too (JWT Keys → Previously used keys → Revoke). Migrated to Supabase's new key format: `SUPABASE_ANON_KEY` env var now holds the new `sb_publishable_...` key, added `SUPABASE_SERVICE_KEY` env var (`sb_secret_...`) — both only in `kulova-backend`'s Vercel prod env, never committed. Verified: old key now gets `401 "Legacy API keys are disabled"` directly from Supabase; new keys work for chat/shopify-sync. `dashboard.html` is now broken (uses the dead key) — known, accepted, fixed in a later step (route it through the backend instead of calling Supabase directly).

**Vaihe 2, Pala 1 (done):** `auth.js`, `portal.js`, `onboard.js`, `stripe.js`, `digest.js` were anon-key-only with no service-key fallback (unlike `chat.js`/`botinfo.js`/`shopify-sync.js`, which already had it) — would have broken the instant RLS policies got tightened. Added the same `SUPABASE_SERVICE_KEY || SUPABASE_ANON_KEY` fallback to all five (branch `service-key-hardening` in `kulova-backend`, deployed to prod). Verified live: onboard.js insert+duplicate-check, auth.js full send→verify→used flow, stripe.js boots clean (no live webhook triggered — real test happens naturally on the next real payment), portal.js Supabase read path (no business currently has a `stripe_customer_id` to test the actual Stripe portal-session path).

**Backup for rollback:** full RLS policy dump (all `qual`/`with_check` expressions) saved at session time to `rls-backup-2026-07-22.json` in the Claude scratchpad dir — use this to restore exact prior policy state if a later RLS change breaks something in production.

**Known, deliberately-deferred bug found along the way:** `digest.js`'s Vercel cron (`0 6 * * *`) shows **zero log entries over a 30-day window**, while other endpoints logged immediately — strong signal the daily digest email has never actually fired (cron registered per `vercel crons ls`, but no execution evidence; possibly a Hobby-plan cron quirk, not yet root-caused). Separately, if `digest_enabled=true` were ever set on a business with `owner_email IS NULL` (true for all Shopify-synced businesses today), `sendEmail(null, ...)` would silently fail per-business — currently dormant since Shopify businesses default to `digest_enabled: false` and there's no UI to change it. **Decide later: fix the cron + null-email guard, or remove the digest feature entirely** (not blocking RLS work).

**Not yet done (vaihe 2 continues):** RLS policy tightening on `login_codes` (next: Pala 2), then `businesses`/`conversations`/`messages`, then route `dashboard.html` through the backend instead of direct Supabase calls. Proceeding one piece at a time, testing after each, asking before anything that touches kulova.com production.
